## Этап 26: употребления идентификатора в текущем буфере

Добавлен Lua API `editor.occurrences` с байтовыми диапазонами, строками,
колонками, лимитом результатов и полным числом совпадений. Поиск использует
текущий буфер и границы целого слова. Это лексический поиск, включая строки
и комментарии, без семантического разрешения. Тесты покрывают границы слов,
ограничение выдачи, Unicode, CR/LF/CRLF и некорректные аргументы.

## Проверочные сборки Linux x64 и Windows x64

Linux-редактор собран из текущего дерева Geany 2.2 development; добавлен
условный INSIGHT_RELOCATABLE для поиска ресурсов в корне распакованного
комплекта. Windows использует официальный Geany 2.1 x64 с GTK и наш модуль,
собранный MinGW GCC 13.2. Сборщик создаёт модуль и восемь проверочных программ.
Добавлены отдельные профили запуска, пример проверки документа, упаковщик
с исходниками, лицензиями, BUILD-INFO и SHA256SUMS. Linux: восемь core-тестов,
восемь parser-примеров и динамическая загрузка модуля проходят. Windows:
PE x64 и разрешение всех импортов модуля проверены; запуск не подтверждён.
GUI обеих платформ требует проверки на целевых машинах. APK не собирался.

## Этап 27: общий сканер употреблений

Лексический сканер перенесён из Lua в переносимое C-ядро. Добавлены строгая
проверка UTF-8, ограничение 2 МиБ, координаты и постраничный C API. Lua использует
тот же сканер; новый набор тестов проверяет границы, Unicode и некорректный ввод.

## Этап 28: постраничный Lua-поиск употреблений

`editor.occurrences(name, limit, offset)` сохраняет старые вызовы и позволяет
получать следующие страницы; полное число возвращается независимо от offset.

## Этап 29: список индексированных файлов

C API возвращает уникальные сортированные пути с фильтром по префиксу и
страницами. Список содержит только файлы с символами; это не файловый manifest.

## Этап 30: Lua-список файлов проекта

`project.files` предоставляет ограниченные страницы уникальных путей индекса.

## Этап 31: расширенный запрос символов в C

Добавлены точный фильтр пути и страницы к существующим фильтрам scope/kind.
Старые функции поиска сохраняют поведение.

## Этап 32: расширенный Lua-запрос символов

options в `project.symbols` добавляет path/scope/kind/limit/offset.

## Этап 33: native workbench в ядре Geany

Постоянная нижняя панель встроена в libgeany, запускается без плагинов.
Жизненный цикл подключён к libmain; это отдельная область от Messages.

## Этап 34: native Scintilla preview

Нижняя панель содержит отдельный read-only Scintilla с UTF-8 текстом текущего
буфера, ограничением 2 МиБ и центрированием текущей строки.

## Этап 35: колоризованный контекст

Preview использует native lexer и стили Geany для типа исходника, номера строк
и выделение целевой строки; отображается полный буфер с исходными номерами.

## Этап 36: автоматический контекст курсора

Изменения текста/выделения и переключение вкладки обновляют native preview
с debounce 60 мс, без диалога и без плагина.

## Этап 37: определение под курсором в контексте

Тег известного идентификатора текущего файла центрируется в нижней панели.
Если определение неизвестно, показывается контекст текущей строки.

## Этап 38: определения в других файлах

Контекст разрешает workspace-теги между открытыми файлами. Открытый буфер
имеет приоритет над диском; чтение диска ограничено и проверяет UTF-8.

## Этап 39: переход по символу внутри preview

Ctrl+click известного идентификатора загружает его определение в цветной нижней
панели. Можно последовательно проходить определения без модального окна.

## Этап 40: открытие определения с центрированием

Open source или Enter из preview открывает файл в основной области, сохраняет
Geany navqueue, центрирует целевую строку и передаёт фокус редактору.

## Этап 41: история нижнего контекста

Back/Forward хранит до 64 посещённых определений. Автоматическое слежение
не засоряет историю; переход из preview сохраняет исходный контекст.

## Этап 42: закрепление контекста

Follow cursor можно отключить. Ручные переходы и история закрепляют preview,
Open source снова включает слежение.

## Этап 43: несколько известных определений

Нижняя панель перечисляет до 256 кандидатных определений с scope/файлом/строкой.
Можно выбрать другое определение без открытия отдельного диалога. Это теги,
а не семантическое разрешение перегрузки.

## Этап 44: встроенный индекс проекта

Переносимое индексное ядро линкуется в libgeany. Native workbench использует
собственный индекс с overlay тегов открытых документов; плагин не требуется.

## Этап 45: native source workspace

Source folder запускает встроенный пошаговый обход и разбор файлов без сборки
проектов. Есть отмена; лимиты 10 000 файлов, 2 МиБ и глубина 64; симлинки и
служебные каталоги пропускаются. Manifest в памяти включает файлы без тегов.

## Этап 46: встроенный Workspace browser

Боковая Workspace-панель ищет проектные символы по префиксу. Выбор строки
показывает цветной контекст; двойной щелчок открывает центрированное определение.

## Этап 47: native outline текущего файла

Workspace переключается на точный путь активного файла, сохраняя scope/kind
и переходы с preview; смена вкладки обновляет outline.

## Этап 48: встроенная панель файлов проекта

Project files фильтрует пути по подстроке без учёта регистра и показывает
до 500 файлов, включая разобранные файлы без символов и открытые документы.
Выбор даёт preview, двойной щелчок открывает файл.

## Этап 49: встроенный поиск употреблений

Usages ищет целый идентификатор в буфере или workspace по одному файлу за idle.
Есть отмена, 10 000 файлов и 2 000 результатов; открытые буферы имеют приоритет.
Выбранное совпадение выделяется в цветном preview при совпадении SHA256 снимка.
Поиск лексический, включает строки и комментарии.

## Этап 50: native индекс между запусками

Завершённый обход без пропусков сохраняет ограниченный CRC32 snapshot через GIO.
Частичный обход не заменяет кэш. Восстановленный список файлов содержит только
файлы с тегами; для полного manifest, в том числе нулевых файлов, нужен Reindex.

## Этап 51: состояние встроенного интерфейса

Сохраняются размер нижней панели, Follow cursor, видимость и выбранный root.
Есть Reindex; настройки имеют версию, ограниченный размер и атомарную запись.

## Этап 52: Lua внутри самого редактора

Lua 5.4.8 и runtime линкуются в libgeany. Встроены загрузка/автозагрузка,
reload/unload расширений и одноразовые скрипты. Native host имеет полный прежний
editor API, Undo-группировку и отдельный снимок индекса на время команды.

## Этап 53: native команды Lua и палитра

Команды расширения встроены в меню редактора и палитру Primary+Shift+P.
Горячие клавиши расширений проверяются на синтаксис и повторения; состояние
Lua сохраняется между вызовами без плагина.

## Этап 54: встроенный интерфейс навигации

Добавлены top-level Navigate и Scripts, View → Context window, клавиши F12,
Primary+T/P/Shift+U и история контекста. Первый запуск показывает Workspace и
нижний preview вместо Messages; Build скрыт. Path/kind убраны из основной
символьной таблицы, путь доступен в tooltip. Заголовок приложения — Geany Insight.

## Этап 55: корректность native навигации

Native tag import выделен в тестируемый модуль: UTF-8, владение строками,
ограничение 250k и приоритет определения в текущем файле. Индекс обновляется
после native обновления тегов и событий документов, не клонируется на каждом
движении курсора. Lua-события работают внутри редактора с read-only host и
снимком индекса. Устаревшие строки/совпадения не дают подтверждённого перехода;
закрытые документы и старые accelerators очищаются.

## Этап 56: завершение native серии и API 0.8

Завершены все 30 этапов 27–56. Main editor Primary-click использует native
проектный resolver. Клавиши поиска не конфликтуют с Print/Ctrl+T upstream.
Предпочтение реальной function-definition проверяется тестом adapter-а.
Добавлены native backend test в Meson/CMake, описание нового интерфейса,
пример Lua и Autotools source metadata. API версии 0.8 сохраняет старые вызовы.
Финальный Git-коммит содержит многострочное описание реализации и проверок.

Проверки: full Linux x64 Geany; core 9/9 CMake+UBSan и compiler runner;
native adapter в Meson и с UBSan; cache/extensions+UBSan; JNI JDK17 -Xcheck:jni;
восемь parser-примеров; Windows x64 native objects с -Werror. GUI не проверен
на целевой машине. Новые APK и бинарные Windows/Linux архивы не выпускались.
Следующий крупный шаг — GUI-проверка и семантический backend, не новые addons.

## Этап 57: стабильное отображение Context

Неизменный текст с прежним filetype больше не устанавливается и не
колоризуется заново при каждом обновлении. Если целевая строка также не
изменилась, сохраняются ручная прокрутка и выделение. Новый текст или тип
файла по-прежнему обновляет подсветку; новая целевая строка центрируется.

## Этап 58: история фактического контекста

Перед явным переходом сохраняется текущая строка каретки превью, даже
если контекст между переходами менялся через Follow cursor. Начальная
позиция записывается только после успешного чтения нового источника;
история по-прежнему ограничена 64 позициями и отбрасывает прежнюю ветку.

## Этап 59: открытие строки каретки превью

Open source и Enter открывают строку, на которую пользователь поставил
каретку в Context, с центрацией в основном редакторе. Follow cursor
включается после успешной проверки документа и строки, сохраняя закреплённый
контекст при неудачном открытии.

## Этап 60: F12 внутри Context

F12 разрешает символ под кареткой превью относительно его исходного файла.
Он использует тот же resolver и выбор определений, что и Ctrl+click,
с сохранением истории и цветным просмотром результата.

## Этап 61: состояние навигации и оформление

Кнопки назад/вперёд отключаются на границах истории, Open source — при
недоступном контексте. Добавлены подсказки клавиш и поведения открытия.
Цвет текущей строки берётся из штатной схемы подсветки вместо фиксированного
светлого фона. Проверки: полная Linux сборка, native index regression,
Windows x64 workbench compilation с -Wextra -Werror. Интерактивный GUI
на целевых ОС не проверен; APK и новые проверочные архивы не собирались.

## Этап 62: открытие выбранной строки результата

Row activation в Workspace и Project files теперь повторно показывает
именно активированную строку перед открытием, а не ранее выбранный Context.
Недоступная строка не считается успешным переходом.

## Этап 63: клавиатурный поиск файлов и символов

Enter в поле поиска открывает первый результат; стрелка вниз выбирает его
и переводит фокус в таблицу. Enter в таблице использует штатный row activation.

## Этап 64: возврат из навигационных панелей

Escape из Context, полей поиска и таблиц Workspace/Project files/Usages
возвращает фокус активному документу, сохраняя результаты поиска.

## Этап 65: закрепление превью при работе мышью

Обычный щелчок в Context отключает Follow cursor до обработки Scintilla,
поэтому отменяется ожидающее обновление, способное сменить источник во время
выделения. Ctrl+click использует тот же закреплённый контекст.

## Этап 66: проверка употреблений при открытии

Двойной щелчок/Enter в Usages повторяет проверку SHA256 результата.
Изменившийся источник блокирует открытие, сразу отключая Open source.

## Этап 67: защита Context от изменения исходника

Context запоминает SHA256 логического текста. Перед переходом в основной
редактор текущий буфер сверяется со снимком; изменение требует обновить
превью. BOM UTF-8 и перевод CRLF в LF не дают ложного отказа. Навигация
использует строки; проверки байтовых диапазонов Usages остаются строгими.

## Этап 68: актуальные списки после отмены обхода

Cancel scan обновляет Workspace, Project files и Context по сохранённому
частичному индексу. Результаты больше не остаются скрыты до ручного поиска.

## Этап 69: сохранение режимов панелей

Workbench settings сохраняет Current file outline и Current buffer only
для поиска употреблений. Старые настройки версии 1 продолжают читаться;
отсутствующие поля оставляют значения по умолчанию.

## Этап 70: перенос длинных строк Context

Новый переключатель Wrap использует перенос Scintilla по словам, не
меняет исходник и сохраняется между запусками редактора.

## Этап 71: адрес каретки для обмена

Copy location копирует в буфер обмена абсолютный путь и текущую строку
каретки Context в виде file:line. Несохранённый или недоступный источник
даёт сообщение вместо неверного адреса.

Серия 62–71 проверена полной Linux x64 сборкой, native index regression и
компиляцией Windows x64 workbench с -Wextra -Werror. Интерактивный GUI на
целевых ОС не проверен. Новые APK и Windows архивы не выпускались.

## Компоновка по официальному Source Insight 4

Изучены официальный Window Tour, скриншот mainappwindow.png, Toolbars,
Project Window и Project Symbol List. Созданы независимая левая панель
File Symbols и правая область с Project Files, Folders, Project Symbols
и Usages. Выбор символов/файлов обновляет нижний Context, включая скрытый;
открытие и переходы внутри него сохраняют существующую защиту снимков.

Символы файла используют непосредственно актуальные TM tags документа,
а проектные символы — общий индекс. Поиск имён поддерживает фрагмент и
не учитывает регистр. Есть сортировки по имени/строке/типу и по имени/пути
файла; дерево сортирует каталоги перед файлами. Списки/дерево включают
распознанные Geany типы файлов, даже без parser-а. Правая ширина и вкладка
сохраняются. Старые вкладки Geany остаются доступными.

Порядок главного меню приведён к File/Edit/Search/Project/Options/Tools/
View/Window/Help с дополнительными Navigate/Scripts. Preferences и прежние
команды Document сохранены в Options. Window переключает открытые документы.
Toolbar получил группу Browse с реальными действиями; стандартные кнопки
Geany сохранены. Полного набора команд и плавающих toolbar Source Insight
пока нет; список отличий — docs/source-insight-layout.md.

Сохранены лексеры, автопреобразование кодировок и plugin API Geany.
Дисковое превью теперь использует тот же механизм encoding auto/BOM, что
редактор, вместо требования входного UTF-8. Полная Windows x64 сборка с
plugins=true и штатными DLL-плагинами прошла. Упаковщик требует включённую
поддержку плагинов и берёт модули из текущей сборки. Прошли Linux build,
тесты encodings и native index; Windows workbench компилируется с -Werror.
Новая компоновка пока не проверена интерактивно на целевых ОС.

## Категории символов и типы файлов

Добавлены правые вкладки Symbol Categories и File Types по описанию Project
Window Source Insight. Категории показывают kind → scope → symbol, фильтруются
по имени, сортируются и связаны с Context. Узлы групп раскрываются, не
сбрасывая Context. Это дерево тегов, не семантическая иерархия классов.
File Types группирует manifest по Geany filetype, определяемому по расширению;
выбор файла даёт preview, активация открывает исходник. Обе вкладки сохраняются
как выбранная проектная вкладка. Поддержка синтаксисов и плагинов сохранена.

Проверены Linux native build и native index regression, Windows workbench
-Wextra -Werror. GUI на целевой машине пока не проверен; полное совпадение
с Source Insight не достигнуто.

## Relations: определения, прямые члены и ссылки

Usages развивается в панель Relations с тремя режимами: лексические ссылки,
определения/объявления по тегам и прямые члены scope. View > Panels > Relation
Window активирует панель. Все режимы используют цветной Context и переход в
исходник. Follow symbol отслеживает слово под курсором основного редактора
независимо от переключателя Follow cursor в Context. Режимы и параметры
сохраняются в workbench.conf без изменения формата раскладок.

Ссылки показывают имя и фрагмент исходной строки, сортируются по заголовкам
колонок. Code only исключает распознаваемые комментарии и строки с сохранением
байтовых координат; включено только по выбору пользователя. Для неподдерживаемых
лексических диалектов файлы пропускаются в этом режиме и учитываются в skipped.
В обычном режиме сохраняется поиск всех лексических употреблений для всех файлов.

Новые backend-тесты проверяют C/C++ raw strings и цифровые разделители, JS-строки,
Python triple quotes, длинные Lua-строки/комментарии, shell-строки, Unicode,
координаты и повреждённый ввод; запросы Relations — квалифицированные scope,
постраничность, прямых членов и определения. Ссылки не разрешают перегрузки
и области видимости семантически; Members не выводит наследование.

## Метаданные символов и прямые связи наследования

Общий индекс хранит signature, type и inheritance из TagManager. Эти строки
владеются индексом, копируются при clone/update и доступны в Lua project.symbols.
Снимок v2 сохраняет новые данные и читает v1, заполняя отсутствующие поля
пустыми строками. Тест проверяет старый формат, новый roundtrip, clone,
усечение, CRC и повреждения полей. Geany plugin ABI не менялся; внутренние
потребители InsightSymbol пересобираются вместе с ядром.

Relations добавляет Base types и Derived types по данным тегов, с переходом
в определения. Поддержаны квалифицированные имена и типичные шаблонные
списки/вложенные типы. Это прямые связи: aliases/imports не разрешаются,
неполные имена могут дать несколько кандидатов. Рекурсивные деревья и
семантический граф вызовов ещё отсутствуют.

При открытии определения на первом слове строки (например class/int) Follow
symbol может выбрать тег объявления той же строки вместо ключевого слова.
Сигнатуры и типы показаны в выборе определения и описании результата Relations.

Исправлен критичный импорт дисковых тегов: tm_source_file_parse в текущем
Geany заполняет tags_array, но для непустого текста возвращает FALSE из-за
старого retry. Адаптер insight_native_parse валидирует UTF-8 и импортирует
полученные теги без зависимости от этого результата. Новый тест использует
реальный C++ парсер и проверяет функцию, сигнатуру, тип, наследование,
отклонение NUL без изменения индекса и очистку по пустому буферу.

## Импорт, экспорт и переименование Bookmarks / Clips

В обе панели добавлены Import и Export с диалогом выбора файла. Экспорт
записывает все записи выбранной панели независимо от поискового фильтра,

Импорт читает и проверяет весь снимок, выбирает записи текущей панели и
объединяет их с существующими. Совпадающие имена в той же категории,

состояние в памяти. Экспорт не меняет профиль.

Закладки сохраняют абсолютные пути: перенос на другой компьютер с иной

лимит; переименование работает и при 64 записях. Подготавливается отдельный
снимок, который становится текущим после успешной записи. Команда помогает
разрешать конфликт имён при импорте. Поисковый фильтр сохраняется: новое имя,
не подходящее фильтру, исчезает из отфильтрованного списка.

## Состав проекта: добавление, удаление и исключения

Project > Add and Remove Project Files и кнопка в правой Project Files
открывают диалог с поиском пути, сортировкой, множественным выбором,
Add files / Add tree / Remove selected / Remove tree / Remove all.

Добавленные папки обходятся после Apply. В списке диалога они отмечены отдельно.

По умолчанию включаются известные типы Geany под base_path. Автодобавление

более вложенное правило дерева переопределяет правило предка.

над одним и тем же файлом/деревом заменяет противоположное действие.
Маски исключений разделяются `;`, чувствительны к регистру и применяются
к имени файла либо относительному пути, включая `vendor/*`.

Правила v1 находятся в [insight-project-files]. Пути внутри проекта
относительны base_path, с `/`; внешние пути абсолютны и могут требовать
поправки при переносе на другую ОС. Ошибочная конфигурация не переписывается
автоматически; до её исправления автодобавление отключено.

## Установленная причина Windows exit 3: отсутствующая база GSettings

## Устранение квадратичной обработки ссылок при выборе файла

При выборе Project Files предпросмотр строил множество имён через страницы index_query по 256 символов. Каждый запрос пересчитывал все N результатов; полное перечисление имело сложность O(N²/256). Добавлен O(1) ordinal-доступ insight_index_at. Множество имён строится одним проходом и переиспользуется до замены индекса; заимствованные указатели удаляются из кеша до освобождения старого индекса.

Обработка имён и подчёркивание идентификаторов Context перенесены в idle-порции с бюджетом 6 мс между итерациями. Новый предпросмотр отменяет предыдущую задачу, смена индекса сбрасывает кеш, завершение редактора удаляет задачу и её буфер. Идентификаторы длиннее 1024 байт не копируются для ссылок, согласованно с ограничением навигации. Чтение файла и первичная окраска пока синхронные; зависание на конкретном пользовательском файле требует Windows-проверки.

Настоящий GUI-сценарий выбирает справа источник 1,4 МиБ со 100000 вызовами известного символа. Проверяет ссылку на последней строке и работу heartbeat-таймера во время обработки. Сценарий Linux прошёл. Core-тест проверяет порядковый проход по 250000 символам и выход за границы.

## Слияние партий символов при обновлении индекса

index_update теперь сортирует только партию нового/изменённого файла и линейно сливает её с сохранёнными символами остальных файлов. Вместо O((N+K) log(N+K)) сортировки на каждом файле — O(N+K log K). Новые строки и буферы выделяются до изменения старого индекса; ошибки входа/выделения памяти оставляют его прежним. Заимствованный путь копируется до освобождения старых записей, входные символы могут принадлежать этому же индексу.

Сравнительный замер одинакового workload 200 файлов по 500 символов: прежний код 2,668 CPU seconds, новый 0,827 CPU seconds (Linux, -O2, один замер). Сериализованные результаты на 100000 символов сравнились побайтно. Это не замер на пользовательском Windows. Проверены полные ключи сортировки, interleaving файлов, повторная замена/удаление с заимствованными входами и модельный сценарий обновлений. UBSan-проверка, все 9 core-тестов и полный GUI-сценарий Linux прошли.
